# テスト駆動開発

TDD は赤 → 緑のループである。このスキルは、そのループが価値あるテストを生むためのリファレンスである: 良いテストとは何か、テストの置き場、アンチパターン、ループの規則。各セクションはすべてのサイクルに適用される — ループの前と最中に参照し、後ではない。

コードベースを調査するとき、存在すれば `CONTEXT.md` を読み、テスト名とインターフェース語彙がプロジェクトのドメイン言語と一致するようにする。触る領域の ADR を尊重する。

## 良いテストとは

テストは実装の詳細ではなく、公開インターフェースを通じて振る舞いを検証する。コードは完全に変わってもよい。テストは変わらないべきである。良いテストは仕様のように読める — 「有効なカートでユーザーがチェックアウトできる」はどの能力があるか正確に伝える — 内部構造を気にしないのでリファクタに耐える。

例は [tests.md](tests.md)、モックの指針は [mocking.md](mocking.md) を参照。

## シーム — テストの置き場

**シーム**とは、テストを置く公開境界である: 内側に手を入れずに振る舞いを観察するインターフェース。テストはシームに置き、内部には置かない。

**事前に合意したシームでのみテストする。** テストを書く前に、テスト対象のシームを書き出し、ユーザーと確認する。未確認のシームではテストを書かない。すべてはテストできない — 事前にシームを合意することが、テスト努力をすべてのエッジケースではなくクリティカルパスと複雑なロジックに載せる方法である。

尋ねる: 「公開インターフェースは何か。どのシームをテストすべきか。」

## アンチパターン

- **実装結合** — 内部コラボレータをモックし、プライベートメソッドをテストし、サイドチャネル（インターフェースの代わりに DB を照会）で検証する。兆候: 振る舞いは変わっていないのにリファクタでテストが壊れる。
- **同語反復的** — アサーションがコードと同じ方法で期待値を再計算する（`expect(add(a, b)).toBe(a + b)`、手で同じ方法で作ったスナップショット、自分自身に等しい定数）。構築上パスし、コードと disagree できない。期待値は独立した正 — 既知のリテラル、計算例、スペック — から来なければならない。
- **水平スライス** — すべてのテストを先に書き、次にすべての実装。一括テストは_想像上の_振る舞いを検証する: _形_をテストし、実変更に鈍感になり、実装を理解する前にテスト構造をコミットする。代わりに**垂直スライス**で進む — 1テスト → 1実装 → 繰り返し。各テストは前のサイクルが教えたことに応える**トレーサー弾**である。

## ループの規則

- **緑の前に赤。** 失敗するテストを先に書き、通すのに十分なコードだけを書く。将来のテストを先取りしたり、投機的な機能を足したりしない。
- **1スライスずつ。** 1サイクルに1シーム、1テスト、最小実装。
- **リファクタリングはループの一部ではない。** レビュー段階（`code-review` スキル参照）に属し、赤 → 緑の実装サイクルには含まれない。
