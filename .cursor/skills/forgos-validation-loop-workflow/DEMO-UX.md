# Demo UX ルーブリック（実証ループ・開示参照）

ForgOS 本体には書かない。検証オーバーレイの **調査分析／利用者／使い勝手／デモ操作／デザイン判断** の正本。  
指揮者と作業者は該当工程の Verifier でここを Yes/No する。

**Leading words:** **sector brief** · **actor-split** · **demo-seeded** · **surface budget** · **attention stack** · **design call**

## ねらい

テーマ語の連想や汎用 CRUD では仕様が甘い。業務アプリでは **業種・業態・顧客属性・現場オペ** の調査分析を先に行い、その帰結として actors／骨格／usability／design call を決める。  
人間に確認せず **AI が調べて決める**。薄い作文はゲート不合格。

## sector brief（必須の調査分析）

業務・店舗・業界・顧客対応がテーマに含まれる（または業務アプリと読める）とき、工程1で **`## sector brief`** を scope に置き、工程2 Source で深化する。非業務と明示できるテーマだけ「非該当＋理由」で免除。

### 調査のやり方（甘さを止める）

- 公開情報・業界通例・典型オペを **当たる**（Web 検索可）。当たった事実と、モデルの推測を **分けて書く**
- 「一般的な小規模店舗」だけで止めない。**業態を1つに絞る**（例: 個人美容室／近所の歯科／2席のカフェ）。絞れないなら複数候補を比較し、デモで採用する1業態を理由付きで決める
- 推測だけで「この業種では必ず〜」と断定したら不合格。根拠または「通例としての仮説」ラベルが必要
- actors・ドメイン骨格・design call・demo-seeded は **sector brief の帰結**として書く。brief と無関係な一般論は不合格

### Scope に最低限そろえる欄（欠けると No）

| 欄 | 合格の目安（甘い例は不合格） |
|----|------------------------------|
| **業種** | 産業分類が具体（美容・飲食・医療・士業など）。「サービス業」単独は不可 |
| **業態** | 規模・提供形態・予約単位が分かる1業態（席／担当者／部屋／メニュー枠など） |
| **顧客属性** | 誰が予約し、何を重視するか ≥2（例: 新規来店／常連、所要時間、指名有無） |
| **現場オペ** | 店側の一日の流れ・ボトルネック ≥2（例: 電話対応、直前キャンセル、担当の空き） |
| **差別化しない通例** | その業態の予約UI／運用で当たり前なこと ≥3（table stakes の種） |
| **スコープに落とす帰結** | brief から採用する actors・主ジョブ・骨格候補への **対応表**（どの発見→どの決め） |

作文チェック: 上記欄が「ありそう」の抽象語だけで、固有の業態オペに触れなければ **再起草**。

## AI が決める範囲（人間に聞かない）

sector brief のあと、AI が決めて成果物に理由を残す:

- actors と主ジョブ（brief の顧客属性・現場オペから）
- 主表面・surface budget・demo-seeded
- attention stack・**design call**（その業態の現場で見慣れた主従）

聞かない例: 業態の好み、色、ブランド、ワイヤー承認。

L2/L3 には usability／行為の **What のみ**。見た目 How は Source／issue／Implement の design call。

## Scope（工程1）

`scope.md` に次がすべて載っていること。

| ID | 条件 |
|----|------|
| S0 | **sector brief** が上記欄を満たす（または非業務で非該当＋理由）。薄い一般論のみなら No |
| S1 | **利用者（actors）** が2役以上。各役の主ジョブ1文。**S0 の帰結である**こと（対応が書ける） |
| S2 | **actor-split:** 役ごとに主表面が別（管理者と一般の主ジョブ同居不可） |
| S3 | **surface budget:** 主要ハッピーパスは **表面 ≤3** |
| S4 | **demo-seeded:** 業態に即した事前選択肢／初期選択の方針（業態の予約単位・典型値が具体） |
| S5 | **attention stack:** 各主表面の視線優先1行以上（現場オペ上の主タスクが先頭） |
| S6 | **品質 What 候補** ≥3（行為・結果の What。ピクセル How 禁止） |
| S7 | **design call（方針）** 1段落以上。**当該業態**の通例に紐づく。汎用「クリーンな管理画面」だけは No |

ドメイン骨格は S0 と整合する概念 ≥5・WF/状態 ≥2。採否は作業者が理由付きで決定（ユーザー採否なし）。

## Source（工程2 Spike）

| ID | 条件 |
|----|------|
| U0 | `## sector brief` — Scope を深化。調査で得た通例／仮説を分離。業態・顧客属性・現場オペが具体のまま残る |
| U1 | `## actors` — S0/U0 帰結と整合 |
| U2 | `## surface map` — 主表面 ≤3、主要 UC の完結場所 |
| U3 | `## demo-seeded` — **業態固有**の初期データ／選択肢（汎用「太郎」「席A」だけなら、業態ラベル付きで足りるか明記。足りなければ No） |
| U4 | `## attention stack` |
| U5 | `## usability what` ≥3。業態オペに根ざす。入力属性羅列のみ不可 |
| U6 | `## design call`／genre look — 通例根拠＋要素 ≥3＋attention 対応。**未決禁止**。他業種の丸コピー感があれば No |

table stakes／domain skeleton も U0 の通例・オペから採る。テーマ語連想だけの骨格は再起草。

## Implement（工程5）

| ID | 条件 |
|----|------|
| I1 | actor-split |
| I2 | demo-seeded（**sector の予約単位・典型値が選択肢に出る**） |
| I3 | surface budget ≤3 |
| I4 | attention stack（現場の主タスクが先頭） |
| I5 | design call 実行（当該業態に見える。汎用管理画面スキン逃げは No）。対応 ≥3 を完了報告 |
| I6 | 単体緑・主要 UC・ドメイン条件は工程表どおり |

## Audit（工程6）— 重大 Gap 候補

- sector brief が無い／一般論のみなのに業務テーマを通している
- actors・文言・選択肢が **業態不一致**（例: 美容なのに「テーブル席」だけ、など帰結崩壊）
- actor-split 破れ、demo-seeded 欠落、surface >3 必須、attention 逆転
- usability what／design call 無視
- 「どの店でも同じ」汎用予約フォームで、brief の通例 ≥3 が UI に無い

軽微: ブランド最終仕上げ（demo-grade 内で業態として認識できれば軽微）
