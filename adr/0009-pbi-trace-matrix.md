# PBI マップは規範 ID 単位の対応表を必須とする

## 文脈

PBI をユーザー価値の一塊にすると、マップが「仕様フォルダ一覧」「`product/apps/web/`」の列挙になり、決め事の各 D# やユースケースが実装・テストのどこかを辿れない。PBI 分割は価値単位を壊しやすい。`specs/` に実装パスは書けない（L1 憲法 §2.4）。

## 決定

1. **PBI の価値粒度は維持**する（無闇に分割しない）。
2. マップの正は **対応表**とする。行は規範アンカー（`<decision-slug>#D<n>` / `usecases/<slug>` / `AC-<n>`）。列は規範・証拠・issue・状態（`covered` / `partial` / `gap`）。
3. フォルダ列挙の「関連仕様」「関連コード」は補助。対応表なしでは `/map` 完了と言わない。
4. glossary 全文や actors 散文は行にしない。決め事の「対象外」は必要なら gap 行で明示する。

## 代替案

- PBI を決め事単位に分割 → hub が増え、価値の一塊が崩れる
- フォルダ列挙のまま → Audit／done で対応が検証できない
- specs に実装パス → L1 憲法 §2.4 に反する

## 却下理由

上記のとおり。粗さの本丸はマップ形式であり、PBI 分割ではない。
