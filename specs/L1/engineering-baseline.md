# L1 工学最低ライン

業務ドメイン規則はここに入れない。違反は Audit およびセッション完了判定で指摘する。
詳細・例外・スタック固有の運用は `specs/L2/decisions/` に書く。

## E1. 秘密情報

秘密情報をログ・コミット・仕様・チャット出力に出さない。例示はプレースホルダを使う。

## E2. 実装の紐づけ

- **`product/`**: L2/L3 の決め事に紐づける（成熟度 draft でも可）。PBI `done`／リリース相当は **stable 以上**（憲法 §4）。
- **`sandbox/`**: **Sourceの試し場**。L2/L3 に紐づく本実装を置かない。
- 紐づけの向きは **仕様 → 実装**（実装パスを仕様に書いて紐づけない。憲法 §2.3–2.4）。

## E3. Audit 可能性

仕様↔実装の乖離と、仕様の拡大解釈を指摘できるようにする。実装は決め事から追跡可能であること。追跡は決め事のパス／ID と issue・PBI・`specs/source`（Source）で行う。**仕様ファイルから実装パスを張って追跡しない**。

## E4. Implement 完了とテスト

Implement セッション完了には、関連する単体テストが緑であることが必須である。

## E5. L1 不可侵

Agent は L1 を直接編集しない。変更案は Steward で提示し、人間承認後に版を上げる。

## E6. 入力検証

信頼境界を越える入力は検証する。未検証の外部入力を権限判定や永続化の主キーにしない。

## E7. 認可

認可されていない主体が他主体の資源を読めない／変えられない設計にする。認可はクライアント信頼にしない。

## E8. 失敗の表現

失敗は呼び出し側が区別できる形で返す（成功と沈黙の失敗を混同しない）。秘密や内部詳細をエラーに載せない。

## E9. 環境分離

環境（少なくとも開発と本番相当）を分離する。本番相当の秘密を開発・examples・ログに置かない。

## E10. インフラ変更の残し方

インフラ変更は先出し検証可能な形でリポジトリに残す。コンソールだけの本番変更を定常手段にしない。

## E11. 破壊的変更

破壊的変更（削除・置換・権限拡大）はレビュー可能な差分として出す。黙って本番に適用しない。
